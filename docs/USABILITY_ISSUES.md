# 실사용 피드백 및 개선 작업

## UX16 — 공급자가 지원하는 서비스 티어 선택

**상태: OpenAI 직접 연결 범위 구현·모의 자동 검증 완료. 실제 계정/모델과 다른 공급자는 미검증.** 모델 호출 시 확인된 공급자에서 서비스 티어를 선택할 수 있다.

2026-09-25 구현: OpenAI 공식 [Chat Completions API](https://developers.openai.com/api/reference/cli/resources/chat/subresources/completions/methods/create)의 `service_tier` 요청/응답 계약과 [Fast mode 안내](https://developers.openai.com/api/docs/guides/fast-mode)를 기준으로 `auto`, `default`, `flex`, `priority`를 직접 OpenAI 프로필+공식 엔드포인트에만 노출한다. `fast`는 공식 문서상 `priority`와 관련되지만 모델별 응답 차이가 있으므로 이 첫 UI 목록에는 넣지 않았다. 모델·계정별 사용 가능 여부는 미확인이며 공급자 거부는 [오류 안내](https://developers.openai.com/api/docs/guides/error-codes)에 따라 그대로 반환하고 다른 티어로 자동 변경하지 않는다. 다른 OpenAI 호환 공급자·Anthropic·Gemini 등은 지원 미확인으로 표시하고 전용 선택을 막는다.

모델 기본 선택은 별도 DB 필드, 에이전트 선택은 `inherit`/명시적 `provider-default`/티어 값이다. 숫자 생성 옵션과 분리한다. 전용 선택은 요청 생성 시 기존 `extraBody.service_tier`보다 우선하며 `provider-default`는 직접 OpenAI 요청에서 이 필드를 제거한다. DB의 고급 설정 자체는 삭제하지 않는다. 기존 모델의 설정이 비어 있으면 고급 값을 그대로 사용하고, 새 모델은 명시적 필드 생략이 기본이다. 적용 버전·실행 스냅샷을 유지하고 모델 시험·초안 시험·MCP 실행에 공통 요청 로직을 쓴다. 모의 자동 시험에서 요청/실제 응답 티어, 응답 값 누락, 거부, MCP 스냅샷, 템플릿·가져오기/내보내기를 확인했다. 아래 ‘현재 구현’과 권장 설계는 변경 전 조사·기준 기록이다.

### 변경 전 구현

서버의 GenerationOptions는 temperature/topP/maxOutputTokens만 정규화한다. 모델/에이전트의 전용 서비스 티어 설정 UI·계약은 없다. 일부 어댑터는 provider extraBody를 요청 본문에 병합하므로 고급 값 전달 경로는 존재하지만, 공급자별 지원 확인·사용자 선택·실효값 표시가 연결된 기능은 아니다.

### 권장 설계

- 모델 설정에 기본 서비스 티어, 에이전트 설정에는 모델 기본값 상속/별도 선택을 제공한다. 프로바이더는 지원 항목과 요청 필드 매핑을 정의하며, 서로 다른 모델의 티어를 하나의 프로바이더 공통값으로 강제하지 않는다.
- 기본 동작은 요청 필드를 생략하는 '공급자 기본값'이다. '상속', '명시적 공급자 기본값(필드 생략)', '명시적 티어 선택'을 구분한다. 공급자가 제공하는 auto 같은 문자열 값은 필드 생략과 동일하다고 가정하지 않는다.
- 우선순위는 에이전트 명시 설정 → 모델 기본 설정 → 공급자 기본 동작이다. 서브 모델이나 메인 모델이 임의로 티어를 변경하는 도구 인자는 이번 범위에 추가하지 않는다.
- 어댑터가 호환된다는 이유만으로 서비스 티어도 같다고 가정하지 않는다. 지원 여부는 공급자 프로필·엔드포인트·모델 제약을 기준으로 정한다. 미지원은 선택 불가, 미확인은 미확인으로 표시한다.
- 구체적인 티어명·허용값·요청 본문/헤더 위치·계정 자격·요금/지연 특성은 **아직 확정하지 않았다**. 구현 시 해당 공급자의 공식 API 문서를 확인하고 프로필 매핑과 확인 근거를 기록한다. 타 공급자의 값을 일괄 전송하지 않는다.
- 기존 extraBody/headers에 같은 의미의 값이 있으면 충돌을 감지한다. 지원되는 기존 값은 UI에서 식별하고 명시적 전용 설정은 요청 생성 시 우선 적용한다. 명시적 '필드 생략'도 고급 설정의 동일 키를 제거해야 한다. 기존 고급 설정을 사용자 모르게 DB에서 삭제하거나 별칭을 추측하지 않는다.
- 에이전트 적용/실행 스냅샷에 실효 선택을 보존하고 모델 응답 시험·초안 시험·공개 MCP 호출·도구 반복의 모든 모델 요청에 같은 계약을 적용한다. 변경 적용 시점은 기존 모델/에이전트 스냅샷 계약을 유지한다.
- 공급자가 티어를 거부하면 명확한 오류를 반환한다. 다른 티어로 조용히 재시도하거나 더 높은 비용의 티어로 자동 승격하지 않는다.
- 요청한 티어와 공급자가 응답으로 알려준 실제 처리 티어를 구분해 기록한다. 응답에 없으면 '확인 불가'이며 요청값을 실제 적용값처럼 표시하지 않는다. 티어 변경으로 MCPex 큐·동시 실행 수·제한시간이 자동 변경되지는 않는다.
- 전용 필드의 타입·검증은 숫자 전용 generationOverrides에 문자열을 억지로 넣지 말고 모델/에이전트/실행 요청 계약에 명시한다. 기존 설정 읽기·템플릿 선택 적용·가져오기/내보내기 호환성을 함께 검토한다.

### 인수 기준

- 지원 공급자에서 모델 기본 선택과 에이전트 상속/재정의/필드 생략이 실제 모의 요청에 정확히 반영된다. 미지원 공급자에는 티어 필드가 전송되지 않는다.
- extraBody/headers의 기존 설정과 충돌·초기화·프로바이더/모델 변경을 검증하며 미지원 값이 이전 선택에서 남지 않는다.
- 시험 호출과 공개 MCP 호출의 모든 모델 턴에 같은 실효 설정이 적용되고, 도구 호출 인자나 생성 내용에 티어 설정이 섞이지 않는다.
- 요청 티어/실제 응답 티어/미확인이 구분되고 거부 시 무단 fallback이 없다. UI 저장·재조회·템플릿·설정 이전의 보존을 확인한다.
- 모의 API 매핑 시험과 실제 계정·모델에서의 지원 확인을 구분한다. 요금·속도 개선은 실제 근거 없이 보장하지 않는다.

> 구현 인계: 공급자 공식 문서로 지원 티어와 매핑을 먼저 확정한 뒤 모델 기본값·에이전트 상속 UI와 요청 계약을 연결하세요. 필드 생략/상속/명시 값 및 기존 고급 옵션 충돌을 구분하고, 요청값과 실제 응답값을 별도로 표시하세요. 제품 API·데이터 명세와 검증 기록을 동기화하세요.

## UX15 — 삭제한 에이전트의 toolName 재사용 차단

**상태: 구현·자동 검증 완료. 실제 사용자 DB와 외부 MCP 재연결은 미검증.**

2026-09-25: DB schema v6에서 미삭제 에이전트만의 부분 유일 인덱스로 변경했다. 생성·복제·초안 변경은 같은 DB 제약을 사용하고 가져오기는 삭제 행을 충돌 대상에서 제외한다. 삭제된 ID·버전·실행은 보존하며 새 동명 에이전트는 새 ID의 비활성·미적용 초안이다. 화면의 삭제·중복 안내 및 API·데이터 명세를 갱신했다. v5 마이그레이션 외래 키·기록, 삭제 후 재생성, 미삭제 중복 409, 동시 생성, 가져오기, MCP 목록 갱신·새 도구 호출을 자동 테스트하고 Edge E2E에서 삭제 후 동명 재생성을 확인했다. 아래 원인 문단은 변경 전 조사 기록이다.

- 사용자는 목록에서 삭제된 test1을 다시 생성하려 했으나 HTTP 409 '동일한 toolName이 이미 있습니다'를 받았다. 이번 확인은 첨부 화면과 소스 대조이며 실제 사용자 DB의 test1 레코드는 조회하지 않았다.
- 삭제는 soft delete로 deleted_at만 설정한다. 목록은 삭제된 행을 숨기지만 DB agents.tool_name의 UNIQUE는 삭제된 행에도 적용된다. API_SPEC에도 삭제된 toolName 재사용 금지가 명시돼 있다. 따라서 현행 정책에 따른 제한이며 브라우저 캐시 문제로 설명하지 않는다. 표시명(displayName) 중복과 MCP 도구명(toolName) 중복을 구분한다.
- 변경 전 오류 안내는 목록 새로고침을 권했지만 삭제된 레코드는 목록에 나타나지 않아 해결할 수 없었다. 당시 우회는 새 toolName 선택이었다.

### 권장 개선안

- 삭제 이력·실행 기록은 유지하고 **미삭제 에이전트 사이에서만 toolName 중복을 금지**한다. 삭제 후 같은 이름의 새 에이전트는 새 agent.id를 부여하며 과거 실행을 새 에이전트에 연결하지 않는다. 기존 재사용 금지 계약을 바꾸는 작업임을 명세에 명시한다.
- DB의 기존 전체 UNIQUE를 제거하고 deleted_at IS NULL 조건의 유일 인덱스로 전환하는 마이그레이션을 설계한다. SQLite 테이블 재구성과 외래 키·인덱스 보존을 확인하고 단순 UI/API 중복 검사만 바꾸지 않는다.
- 생성·복제·이름 변경·가져오기의 충돌 판정을 같은 정책으로 맞춘다. 특히 현재 가져오기는 삭제 행까지 SELECT tool_name FROM agents로 수집하므로 함께 변경해야 한다. 대소문자 비교 규칙은 기존 API/DB 차이를 확인하고 일관된 계약을 명시한다.
- 삭제된 에이전트의 ID·버전·이름과 실행 기록은 보존한다. 실제 사용자 DB를 임시 SQL로 삭제하거나 과거 이름을 임의로 바꾸는 우회는 하지 않는다.
- MCP 목록 갱신·재연결에서 새 ID/적용 버전의 도구가 노출되는지 확인한다. 같은 이름을 기억하는 외부 클라이언트가 있으므로 새 에이전트는 기존 생성 규칙대로 비활성·미적용 상태에서 시작하고 사용자가 적용·활성화한다.
- UI 삭제 안내의 'toolName 재사용 불가' 문구와 API_SPEC 등 관련 계약을 동기화한다.

### 인수 기준

- 비활성 에이전트 생성→삭제→같은 toolName 재생성이 성공하고 미삭제 동명 에이전트 생성은 409다. 활성 에이전트 삭제 제한은 유지한다.
- 과거 실행은 이전 agent.id/버전에 남고 새 에이전트의 기록과 섞이지 않는다. 삭제 이름 재사용·가져오기·복제·동시 생성 충돌을 검증한다.
- 기존 DB 마이그레이션 후 외래 키 무결성과 실행 기록 조회를 확인한다. MCP 목록 갱신 후 새 적용 버전만 호출되고 삭제된 에이전트가 되살아나지 않는다.
- UI에서 삭제/재생성 흐름과 오류 안내를 검증한다. 정책 유지 또는 변경의 구현 결과를 문서에 정확히 반영한다.

## UX14 — 전달된 파일 경로를 모델이 축약하는 문제

**상태: 설계 완료·구현 계획·미검증.** 사용자 제공 시험 보고에서 메인이 전달한 절대 경로 대신 서브 모델이 파일명만 읽어 ENOENT가 발생했고, 폴더 목록 조회 실패 후 지정 파일 직접 읽기로 복구하지 못했다. 이번 문서화에서 해당 실험을 재실행하지 않았으며 테스트 파일 자체의 권한 문제나 모델의 쓰기 능력으로 단정하지 않는다.

해결 방향은 프롬프트만 보강하는 것이 아니라, MCPex가 선택 입력 targets를 검증해 실행별 대상 ID에 연결하는 것이다. 서브 모델은 대상 ID 기반 파일 도구를 사용하며 경로를 임의 축약/대체하지 못한다. 구체적 입력·권한·기존 호환성·회귀 기준과 인계 지시는 [대상 파일 지정 설계](TARGET_FILE_DESIGN.md)를 따른다. 기존 UX09/UX12 경로 처리를 대체하지 않고 공통 실행기로 재사용한다.

## UX13 — 등록된 프로바이더 편집 진입점 누락

**상태: 구현·자동 검증 완료.** 등록된 프로바이더 카드에서 설정과 인증값을 편집할 수 있다. 실제 외부 공급자 연결과 기존 사용자 데이터로의 수동 확인은 미검증이다.

구현 결과: 상세 조회 후 동일 ID로 revision을 확인하며 PATCH한다. 프로필 선택 시 바뀔 어댑터·실행 위치·URL을 저장 전에 보여주고, 숨겨진 headers·extraBody는 보존한다. API 키는 유지가 기본이며 교체·제거는 별도 요청으로 수행한다. 설정만 저장되고 키 작업이 실패하면 저장된 설정을 반영한 채 키 작업을 재시도할 수 있다. 충돌 시 편집값을 보존하고 최신 저장값 조회와 명시적 다시 불러오기를 제공한다. 저장된 설정으로 별도 모델 조회 시험을 할 수 있다.

### 확인한 문제

- `apps/web/src/main.tsx`의 프로바이더 화면은 등록 폼과 목록의 삭제 버튼만 제공한다. 등록된 항목의 이름·주소·요청 제한시간·리소스 그룹 등을 수정하는 편집 진입점이 없다.
- 서버에는 `GET/PATCH /api/v1/providers/:id`와 인증값 교체/제거 API가 이미 있다. PATCH는 expectedRevision으로 충돌을 검사한다. 따라서 백엔드 수정 기능 전체가 없는 것이 아니라 화면 연결이 빠진 상태다.

### 해결 방안

- 각 프로바이더 카드에 편집 버튼을 추가하고 기존 등록 폼을 편집 모드로 재사용하거나 같은 필드의 편집 영역을 제공한다. 현재 값을 불러오고 저장·취소·미저장 변경 안내를 제공한다.
- 이름, 프로필/어댑터, 로컬/클라우드 구분, base URL, 동시 실행 수, 리소스 그룹/그룹 동시 실행 수, 요청당 제한시간을 수정할 수 있게 한다. headers/extraBody 등 기존 고급 설정은 편집에서 누락되더라도 저장 시 보존한다. 프로필 변경 시 바뀌는 값은 미리 보여주고 기존 값을 조용히 덮어쓰지 않는다.
- 동일 provider.id로 PATCH해 연결 모델·에이전트 참조를 유지한다. 삭제 후 재등록 방식으로 구현하지 않는다. 성공 후 모델 선택기의 프로바이더명과 관련 화면도 갱신한다.
- API 키는 원문을 다시 표시하지 않고 저장 여부만 표시한다. 기존 키 유지(기본)·새 키로 교체·키 제거를 명확히 구분한다. 빈 입력이나 마스킹 문자열을 새 키로 저장하지 않는다.
- 설정 저장과 인증값 변경은 별도 API다. 두 작업의 revision 변화와 일부 성공/일부 실패를 처리하고, 전체 성공처럼 표시하지 않는다. 충돌 시 입력을 보존하고 최신 설정 확인/재시도 경로를 제공한다.
- 연결 주소/어댑터 변경이 기존 모델 ID와 호환되는지 사용자가 확인할 수 있게 안내한다. 저장만으로 연결 성공을 선언하지 말고 별도의 연결/모델 조회 시험 결과를 표시한다. 진행 중 실행과 대기 작업에 대한 적용 시점은 현재 실행 스냅샷 계약을 확인해 설명한다.

### 인수 기준

- 등록된 프로바이더를 UI에서 수정·저장하고 새로고침 후 값이 유지된다. 취소하면 원래 설정이 유지된다.
- 요청당 제한시간과 동시 실행/그룹 값을 수정할 수 있고 서버의 허용 범위 오류가 입력 근처에 표시된다.
- 이름 변경 후 모델 표시에 새 프로바이더명이 반영되며 모델·에이전트 참조와 활성 상태가 유지된다.
- 기존 키 유지·교체·제거, 일반 설정만 수정, revision 충돌, 설정/키 변경 일부 실패를 각각 검증한다. 인증값은 응답·화면·로그에 노출하지 않는다.
- 고급 설정 보존, 편집 대상 전환, 미저장 취소, 프로필 변경의 값 반영을 검증한다. 기존 API 테스트 통과를 편집 UI 완료로 간주하지 않는다.

> 구현 인계: UX13의 프로바이더 편집 UI를 기존 조회/PATCH·인증 API에 연결하세요. 참조 ID와 고급 설정을 유지하고, 키 유지/교체/제거 및 revision 충돌·부분 실패를 구분하세요. UI 흐름 검증 후 구현 상태와 테스트 문서를 갱신하세요.

## 2. UX01 — 삭제 진입점과 초안 정리

**상태: 구현 완료·자동 검증 완료.** 실제 사용자 데이터로 삭제 영향을 확인하는 수동 검증과 키보드·스크린리더 검증은 남아 있다.

### 확인한 현상과 코드

- 프로바이더·모델: `apps/server/src/index.ts`에 `DELETE /api/v1/providers/:id`, `DELETE /api/v1/models/:id`가 있으나 `apps/web/src/main.tsx`에는 이를 호출하는 삭제 UI가 없다.
- 에이전트: `deleteAgent`와 삭제 버튼은 존재하지만 편집 화면의 템플릿·복제 관련 영역 안쪽에 배치되어 있다. 활성 에이전트는 버튼이 비활성화되어 삭제 절차를 이해하기 어렵다. 서버는 비활성 에이전트만 soft delete한다.
- 초안: 별도의 초안 폐기 UI/API는 확인되지 않았다. 저장된 미적용 에이전트를 지우는 것과, 적용된 에이전트의 수정 초안만 버리는 것은 다른 작업이다.

### 수정 작업

1. 프로바이더·모델·에이전트 목록 또는 각 상세 화면의 일관된 위치에 삭제 동작을 제공한다. 대상 이름과 삭제 영향을 확인할 수 있어야 한다.
2. 참조 중 모델·프로바이더는 기존 서버의 삭제 차단을 유지한다. 관련 모델·에이전트와 먼저 수행할 정리 동작을 안내한다. 연쇄 삭제를 기본 동작으로 추가하지 않는다.
3. 활성 에이전트에는 비활성화가 선행되어야 함을 표시한다. 삭제 성공 후 목록·선택 상태·관련 선택지를 갱신하고 실패 시 현재 편집 내용을 유지한다.
4. 초안 관련 동작은 다음 의미를 구분해 설계한다: 미저장 편집 취소, 아직 적용한 적 없는 에이전트 전체 삭제, 적용 버전이 있는 에이전트의 초안 변경 폐기. 마지막 동작은 공개 버전과 활성 상태를 변경하지 않아야 한다.
5. 초안 변경 폐기의 복원 원본과 동시 편집 revision 처리는 구현 전에 명세를 보완한다. 적용 스냅샷을 무조건 초안 구조로 덮어쓰지 않는다.

### 인수 기준

- 미참조 프로바이더·모델과 비활성 에이전트를 UI만으로 삭제할 수 있고 새로고침 후에도 목록에서 사라진다.
- 참조 중 삭제 실패 및 활성 에이전트 삭제 제한에 대상과 해결 순서가 표시된다.
- 삭제 확인 취소는 데이터를 변경하지 않는다. 기존 실행 기록·toolName 재사용 정책을 유지한다.
- 적용 전 초안 에이전트를 정리할 수 있다. 적용 후 초안 변경을 폐기하는 경우 공개 도구 설정·활성 상태·기존 실행 기록을 유지한다.

## 3. UX02 — 설정별 시험 입력

**상태: 구현 완료·자동 검증 완료.** 실제 사용자 스키마의 모든 조합과 스크린리더 수동 검증은 남아 있다.

### 확인한 현상과 코드

`main.tsx`의 `testInputText`는 고정된 task 예제로 시작하고 일반 textarea에서 JSON 원문을 받는다. `previewOrTest`가 `parseObject`를 호출하며 일반 문장, 배열, 잘못된 JSON을 모두 “시험 입력은 JSON 객체여야 합니다.”로 처리한다. 현재 에이전트의 스키마별 입력 폼과 예제 생성은 없다. 최상위 object 계약 자체는 기존 제품 명세에 명시되어 있다.

### 수정 작업

- 현재 초안의 `inputSchema`를 기준으로 필수 여부·설명·타입·기본값을 보여주는 시험 입력 폼을 제공한다. 일반 텍스트 항목은 사용자가 JSON을 작성하지 않아도 내부에서 객체로 조립한다.
- task 고정 매핑을 모든 설정에 강제하지 않는다. 이름이 다른 필드, 여러 필수 필드, 숫자·boolean·enum 등에 대응한다.
- 고급 JSON 편집을 함께 제공하고, 폼으로 표현하기 어려운 중첩 객체·배열에는 예제와 구체적인 오류 위치를 제공한다. 미지원 스키마를 조용히 누락하지 않는다.
- 템플릿·에이전트·스키마 변경 시 입력 폼과 예제를 갱신한다. 기존 입력을 무조건 삭제하지 말고 유지 가능한 값과 다시 입력할 값을 구분한다.
- JSON 구문 오류, 최상위 타입 오류, 스키마 필수 항목·타입 오류를 구분한다. 오류를 해당 입력 근처에 표시한다.
- 실행 폴더 정책의 별도 요청 필드 `workspace`와 `input.workspace` 템플릿 값을 구분해 안내한다. 입력값이 실행 권한을 대신하지 않도록 한다.

### 인수 기준

- 일반 응답·코드 작업 템플릿 및 사용자 정의 필드 스키마에서 각각 올바른 입력으로 미리보기·시험 실행이 가능하다.
- 일반 문장을 텍스트 폼에 입력하면 올바른 객체로 전송된다. 고급 JSON 모드에서는 잘못된 JSON과 타입을 정확히 안내한다.
- 에이전트 전환·스키마 변경 후 이전 필드가 잘못 섞이지 않는다. 누락된 필수 필드는 모델 호출 전에 식별된다.

## 4. UX03 — 시험 상태와 최종 결과 자동 표시

**상태: 구현 완료·자동 검증 완료.** 실제 장시간 모델 및 모든 terminal 오류 상태의 브라우저 수동 검증은 남아 있다.

### 확인한 현상과 코드

서버의 `POST /api/v1/agents/:id/test-runs`는 `202 { runId, status: 'queued' }`로 비동기 접수한다. `previewOrTest`는 이 응답만 `agentResult`에 넣고 한 번 `reload()`한다. 해당 실행을 완료까지 추적하여 결과 영역을 갱신하는 UI 연결이 없다. 실행 상세 조회와 이벤트 API는 이미 존재한다.

### 수정 작업

- 접수 직후 같은 시험 영역에 대기·실행 중 상태를 표시하고 `runId`를 추적한다.
- 기존 실행 조회 API 폴링 또는 이벤트 API를 연결해 완료 시 최종 출력, 실패 시 오류와 확보된 결과를 자동 표시한다. 방식은 구현 시 선택한다.
- 일반 답변을 읽기 좋은 형태로 표시하고 원시 응답·실행 상세는 별도 펼침으로 제공한다. 실행 기록으로 이동하지 않아도 결과를 확인할 수 있어야 한다.
- 취소·시간 초과·연결 끊김을 무한 대기와 구분한다. 화면 전환 시 구독을 정리하고 이전 실행의 늦은 응답이 다른 에이전트의 결과를 덮어쓰지 않게 한다.
- “바로 표시”는 모델 완료를 기다리지 않는다는 뜻이 아니라, 상태를 즉시 표시하고 완료 후 수동 새로고침 없이 결과를 보여준다는 뜻이다. 토큰 스트리밍은 이 수정의 필수 조건이 아니다.

### 인수 기준

- 느린 모의 모델에서도 접수 직후 진행 상태가 보이며 완료 후 같은 영역에 최종 답변이 자동 표시된다.
- 실패·취소·시간 초과가 종료 상태로 표시되고 연결 실패 시 재조회 동작이 제공된다.
- 연속 시험 및 시험 중 에이전트 전환에서 결과가 잘못 연결되지 않는다.

## 5. UX04 — 스크롤 위치와 무관한 알림

**상태: 구현 완료·모의 브라우저 검증 완료.** 실제 사용자 화면의 좁은 창·키보드·스크린리더 수동 검증은 남아 있다.

### 확인한 현상과 코드

`main.tsx`의 `uiError`와 `message`는 내비게이션 다음, 현재 화면 앞에 렌더링된다. 에이전트 설정 하단에서 저장·검증 실패가 발생해도 상단 알림이 화면 밖에 있어 인지하기 어렵다.

### 수정 작업

- 저장·적용·생성·삭제·시험 접수 안내는 화면에 고정된 토스트 또는 알림 영역으로 제공한다. 특정 컴포넌트 구현은 미확정이다.
- 오류는 읽기 전에 자동으로 사라지지 않게 하고 닫기·상세 확인을 제공한다. 필드 오류는 입력 근처에도 표시한다.
- 단순 성공 안내가 편집 포커스나 스크롤 위치를 빼앗지 않게 한다. 사용자 판단이 필요한 삭제 확인 등에 대화상자를 사용한다.
- 키보드 접근, 스크린리더 알림, 좁은 화면에서의 버튼·입력 가림을 확인한다.

### 인수 기준

- 긴 에이전트 편집 화면 최하단에서 성공·오류 알림을 스크롤 없이 확인할 수 있다.
- 오류 상세·닫기를 조작할 수 있고 입력 내용과 편집 위치가 유지된다.
- 여러 안내가 연속 발생해도 중요한 오류가 즉시 덮이거나 사라지지 않는다.

## 6. UX05 — MCP 등록 정보 탭

추가 사용자 요청: MCP 등록 방법과 에이전트별 등록 여부를 화면에서 이해할 수 있는 정보 탭을 제공한다. **구현 완료·자동 검증 완료** 상태이며 실제 사용자 MCP 클라이언트 등록은 미검증이다.

### 현재 구조

MCP 클라이언트마다 MCPex 서버 연결을 한 번 등록한다. 활성 에이전트 각각이 자신의 `toolName`을 가진 MCP 도구로 노출된다. 에이전트별 서버 등록은 필요하지 않다. 프로바이더와 모델은 에이전트 내부 설정이며 독립 MCP 도구로 자동 노출되지 않는다.

권장 연결은 STDIO이며 실행 파일은 Node.js, 인수는 CLI의 절대 경로와 `mcp`다. `apps/cli/src/index.ts`의 `mcp` 분기는 로컬 서비스를 필요할 때 시작하고 `ToolCatalogBridge`로 활성 도구 목록을 전달한다. 비활성 상태는 재시작 후에도 유지된다. 도구 목록 갱신을 반영하지 않는 클라이언트는 재연결이 필요할 수 있다.

### 수정 작업

- 사용자가 찾기 쉬운 **MCP 연결 정보** 탭을 제공한다. 서버 1개 등록 → 활성 에이전트별 도구 제공 구조를 짧은 예시로 설명한다.
- 현재 설치 환경에 맞는 실행 파일 경로와 인수 배열을 구분해서 표시하고 복사 버튼을 제공한다. 공백이 포함된 경로를 지원하고 개발자 PC 경로를 고정하지 않는다.
- 일반 등록 필드: 전송 방식 `STDIO`, 명령 `node` 또는 확인된 Node.js 절대 경로, 인수 `["<설치 경로>/apps/cli/dist/src/index.js", "mcp"]`. `open`은 설정 화면용이며 MCP 등록 명령이 아님을 안내한다.
- 활성 도구의 이름·설명과 비활성 에이전트 상태를 보여준다. 활성 도구가 0개이면 적용·활성화 절차를 안내한다.
- 최초 등록, 설정 저장·적용·활성화, 연결 확인, 목록 갱신 또는 재연결 절차를 제공한다. 사용자 지정 데이터 경로 등 실제 필요한 환경변수가 있으면 안내한다.
- 로컬 서비스 정상 여부와 실제 MCP 클라이언트 연결 검증을 구분한다. 서비스 health 성공만으로 클라이언트 연결 완료를 표시하지 않는다.
- 인증 토큰·API 키는 등록 예제와 복사 내용에 포함하지 않는다. 클라이언트별 설정 형식은 구현 시 공식 자료로 확인하고 검증한 형식만 제공한다.

### 인수 기준

- 탭의 정보만으로 서버를 한 번 등록하고 활성 에이전트 2개를 서로 다른 도구로 조회·호출할 수 있다.
- 비활성 에이전트는 도구 목록에 없고, 활성화·비활성화 시 서버 등록을 다시 만들 필요가 없다. 필요한 클라이언트 재연결 절차는 안내된다.
- 공백이 포함된 설치 경로의 복사 값을 사용해 STDIO 연결이 성공한다. 예제에 비밀정보가 없다.
- 도구가 0개인 상태와 서비스 연결 실패 상태에서 각각 다음 조치를 알 수 있다.

## 8. UX06 — 실제 등록 화면에 맞는 MCP 연결 안내

**2026-09-18 개선 구현·자동 검증 완료 / 실제 사용자 Codex 도구 목록·호출 검증 미수행.**

현재 탭은 실행 파일·인수 배열·환경변수 JSON을 제공하지만 사용자는 Codex 등록 화면의 각 칸에 무엇을 넣는지 알기 어렵다고 보고했다. 첨부 화면에는 이름, 유형, 실행 명령, 개별 인자 추가, 환경변수 키/값, 환경변수 패스스루, 작업 중인 디렉터리가 있다. 기존 탭의 기능 테스트 통과를 등록 사용성 검증 완료로 보지 않는다.

### 요구사항

- 연결 목적을 같은 PC에서 Codex에 등록하는 경우와 외부 네트워크에서 연결하는 경우로 구분한다.
- Codex 화면의 필드명과 순서에 맞춰 현재 환경의 값을 표시한다. 실행 명령은 실행 파일 하나, 각 인자는 독립된 값으로 제공하고 JSON 배열 전체를 인자 한 칸에 붙이는 혼동을 없앤다.
- 환경변수도 한 줄당 키/값으로 표시하고 필수·선택을 구분한다. 패스스루와 작업 디렉터리는 필요한지, 비워도 되는지 안내한다. 클라이언트의 작업 디렉터리와 에이전트의 파일 접근 정책을 구분한다.
- 원시 경로와 JSON 이스케이프 표현을 구분한다. 화면 입력칸용 복사에서는 JSON 따옴표·대괄호·중복 백슬래시가 섞이지 않아야 한다.
- 지원 클라이언트에서 가능한 설정 파일/명령 방식은 공식 형식을 확인한 뒤 전체 설정 복사도 제공한다. 일괄 등록을 지원하지 않는 UI는 최소한 필드별 그대로 붙여넣기를 보장한다.
- 저장 후 실제 도구 목록에서 활성 에이전트를 확인하는 완료 기준을 제공한다. 로컬 서비스 health는 클라이언트 등록 성공과 구분한다.

### 외부 네트워크 연결

현재 CLI 서버는 loopback 주소에 바인딩되고 로컬 사용자 인증을 사용한다. 현재 로컬 주소를 외부 접속 주소처럼 제공해서는 안 된다. STDIO와 원격 HTTP 연결을 구분하고 원격 기능은 구현 전까지 미지원으로 표시한다.

원격 제공을 위한 바인딩·공개 URL·TLS·인증 발급/폐기·관리 화면과 MCP 접근 분리·접근 범위·연결 시험을 별도로 설계한다. 단순 포트 공개나 로컬 인증 토큰 복사를 완성된 등록 절차로 안내하지 않는다. 원격 경로는 MCPex 실행 호스트의 파일 경로라는 점도 명확히 한다. 구체적인 인증·배포 방식은 미결정이며 이번 요청에서는 네트워크 설정을 변경하지 않는다.

### 인수 기준

- 새 사용자가 Codex 등록 화면에서 추가 추론 없이 표시된 값을 복사해 등록하고 도구 목록을 확인한다.
- 공백 있는 Windows 경로, 인자 2개, 환경변수 키/값과 선택 필드가 올바르게 입력된다.
- 외부 연결 지원 여부를 즉시 이해할 수 있다. 구현 후에는 다른 호스트에서 인증된 접속과 인증 없는 접속 거부를 각각 검증한다.
- 사용자 요청에 따라 MCP 등록 절차는 개선이 완료되기 전 README에 싣지 않는다.

### 구현 및 검증 결과

- Codex 등록 화면의 순서에 맞춰 이름 `mcpex`, 유형 `STDIO`, 실행 명령, 인자 2개, 환경 변수 키/값, 환경 변수 패스스루, 작업 중인 디렉터리를 각각 표시한다. 인자와 환경 변수는 한 항목씩 복사하며 화면 입력용 값에는 JSON 따옴표·배열·이스케이프 백슬래시를 붙이지 않는다.
- 환경 변수 패스스루와 작업 중인 디렉터리는 현재 등록에서 비워 두도록 안내하고, 작업 중인 디렉터리가 에이전트의 파일 접근 정책과 다름을 표시한다.
- 공식 Codex `config.toml`의 `[mcp_servers.mcpex]` 형식으로 전체 설정을 생성해 복사할 수 있다. TOML에서는 Windows 경로를 이스케이프하지만 필드별 복사 값은 원시 경로를 유지한다.
- 같은 PC의 로컬 STDIO 등록과 다른 PC 연결을 분리했다. 원격 연결은 현재 미지원이며 loopback 주소나 로컬 인증 토큰을 외부 연결 정보로 사용하지 않도록 경고한다.
- 생성기 단위 테스트에서 공백 있는 Windows 경로, 인자 2개, 환경 변수 키/값과 TOML 출력을 확인했다. Edge E2E에서 필드 순서, 개별 인자 `mcp`의 실제 클립보드 값, 전체 설정 복사와 원격 미지원 안내를 확인했다.
- 설치된 Codex CLI의 일회성 `-c` 설정으로 생성한 command/args를 읽어 `stdio`, 인자 2개, 빈 `env_vars`와 `cwd: null`로 해석되는 것을 확인했다. 사용자 설정을 변경하는 실제 영구 등록, `/mcp` 도구 목록과 호출·재연결은 T14에 남아 있다.

## 9. UX07 — 전체 파일 접근 허용 정책

**2026-09-18 구현·자동 검증 완료 / Windows 다중 드라이브·UNC 및 실제 OS 권한 거부 수동 검증 미수행.** 사용자가 명시적으로 선택하면 폴더를 미리 한정하지 않고 현재 MCPex 프로세스의 OS 사용자 권한 범위에서 파일에 접근한다. 기존 에이전트 설정은 자동 변경하지 않는다.

### 요구사항과 설계 범위

- 사용 안 함·고정 폴더·호출자 폴더와 별도로 전체 접근 선택지를 제공한다. 기존 에이전트의 정책을 자동으로 바꾸지 않는다.
- 전체 접근은 MCPex 프로세스의 OS 사용자 권한으로 접근 가능한 파일 범위이며 관리자 권한 상승을 의미하지 않는다. 원격 사용 시에도 실행 서버의 파일 범위다.
- 읽기/쓰기 가능 여부는 여전히 에이전트에 선택한 허용 도구에 따른다. 폴더 제한을 없애는 것과 모든 도구·명령을 켜는 것을 구분한다.
- 현재 파일 도구는 단일 root와 상대 경로만 받으므로 드라이브 루트를 하나 지정하는 임시 대응으로 전체 접근을 구현하지 않는다. 절대 경로, 여러 드라이브, 상대 경로 기준 디렉터리, UNC·링크 정책을 정하고 공통 경로 처리에 반영한다.
- 넓어진 접근 범위가 폴더 충돌 잠금·동시 실행에 미치는 영향을 설계한다. 서로 다른 기준 폴더로 동일 파일에 접근할 때 잠금을 우회하지 않도록 한다.
- 시간·결과 크기·파일 기대 해시·명령 allowlist는 별도 정책으로 유지한다. 적용·내보내기·가져오기·개인 템플릿에서의 권한 보존/초기화 규칙도 함께 정의한다.
- 선택 시 범위를 짧게 설명하고 저장·적용 후 실효 권한이 화면에 드러나게 한다.

### 인수 기준

- 통제된 임시 폴더들로 고정 루트 밖 파일 접근과 읽기 전용/쓰기 도구 구분을 검증한다. 기존 fixed/caller 제한은 유지된다.
- OS 권한 거부가 명확한 오류로 표시되고 권한 상승을 시도하지 않는다.
- 절대/상대 경로·드라이브·링크 정책과 동시 편집 충돌 처리에 회귀 검증이 있다.

### 구현 및 검증 결과

- 작업 폴더 정책에 `full`을 추가했다. 허용 루트는 저장하지 않으며 파일 경로와 `run_command.cwd`는 모두 절대 경로만 허용한다. 따라서 상대 경로 기준 디렉터리를 임의로 추론하지 않고 Windows 드라이브·UNC 경로는 Node의 네이티브 절대 경로 처리에 맡긴다.
- 전체 접근도 선택한 도구와 등록한 명령만 모델에 제공한다. 시간·결과 크기·기대 해시·명령 allowlist는 그대로 유지하고, 현재 사용자 권한의 `EACCES`/`EPERM`은 `ACCESS_DENIED`로 표시한다. 관리자 권한 상승은 수행하지 않는다.
- 모든 경로 요소의 심볼릭 링크/junction을 차단한다. 전체 접근 실행은 전역 파일 잠금을 사용해 고정·호출자 폴더 작업을 포함한 다른 모든 파일 작업과 직렬화하며, 서로 다른 기준 경로로 같은 파일 잠금을 우회하지 못하게 했다.
- UI에 고위험 선택지와 OS 사용자 권한 범위, 절대 경로 요구를 표시하고 편집 화면과 MCP 연결 화면에서 적용 버전의 `full` 상태와 실효 도구를 확인할 수 있게 했다. 설정 내보내기·개인 템플릿은 기존 환경 의존 정책 정리 규칙에 따라 `none`으로 초기화한다.
- 임시 폴더 두 곳의 절대 경로 읽기, 상대 경로 거부, 읽기/쓰기 도구 분리, 전체 접근과 scoped 작업의 전역 직렬화, 정책 저장·적용·연결 카탈로그를 자동 검증했다. Edge E2E에서 고위험 안내와 저장·적용·연결 화면의 실효 상태도 확인했다. 실제 Windows 다중 드라이브·UNC 공유, junction 및 OS ACL 거부 화면은 수동 검증으로 남긴다.

## 10. UX08 — 호출자 폴더 설명과 유효 설정 검사

**2026-09-18 개선 구현·자동 검증 완료 / 실제 Codex 사용자 정의 메타데이터 전달 미확인.** 현재 호출자 폴더는 클라이언트 현재 폴더를 자동 감지하지 않는다. 관리 시험은 본문의 별도 workspace, MCP는 `_meta["io.mcpex/workspace"]`로 전달하며 일반 입력의 input.workspace와 다르다.

- 허용 루트 `C:\Work`, 시험 호출 폴더 `C:\Work\ProjectA` 예시를 정책 옆에 제공한다. 허용 루트는 경계이고 실제 작업 폴더는 매 호출 값임을 설명한다.
- 일반적인 클라이언트의 프로젝트 폴더 전달 방식과 지원 여부를 확인한다. 메타데이터를 보낼 수 없는 경우 사용자 입력 또는 설정 기본 폴더를 통한 대안을 설계하며 기존 권한 경계는 유지한다. 정확한 API 변경은 미결정이다.
- 코드 작업 모드와 파일 도구가 선택되어도 정책 none이면 실행 시 파일 도구가 제공되지 않는 현재 동작을 개선한다. 저장·적용 전 문제와 해결 방법을 표시하고 실효 도구 목록을 보여준다.
- 등록되어 활성화된 상태와 실제 파일 작업 가능한 상태를 구분한다.

인수 기준: 호출자 폴더 예시만으로 UI 시험에 성공하며 누락/범위 밖 입력을 이해할 수 있다. 실제 대상 클라이언트에서도 작업 폴더 전달을 확인한다. 도구 모드+정책 none 설정을 사용자가 모르고 파일 작업 가능한 상태로 인식하지 않도록 한다.

### 구현 및 검증 결과

- 정책 편집 화면에 허용 루트와 실제 호출 폴더의 차이, UI 시험 본문과 MCP `_meta`의 전달 방식, `input.workspace`와의 차이를 예제와 함께 표시한다.
- 공식 OpenAI 문서는 MCP 서버 `cwd`를 서버 프로세스 시작 디렉터리로 정의하지만 MCPex 전용 `_meta` 자동 전달은 명시하지 않는다. 일반 Codex 등록이 현재 프로젝트를 자동 전달한다고 안내하지 않으며, 사용자 정의 메타데이터를 보내지 못하는 클라이언트에는 고정 폴더 정책을 대안으로 제공한다. 권한 경계를 약화시키는 자동 fallback은 추가하지 않았다.
- 초안의 실행 모드·작업 폴더 정책·선택 도구를 조합해 실효 도구 목록을 표시한다. 도구 모드+정책 `none`, 도구 미선택, 응답 모드, 고정 폴더, 호출자 폴더 조건부 상태를 구분한다.
- MCP 연결 화면은 적용 버전 기준으로 에이전트가 활성 등록된 것과 내부 파일·명령 도구가 실제로 가능한 것을 구분한다.
- 실효 도구 단위 테스트, 연결 API 적용/초안 격리 테스트, 기존 caller workspace 통합 회귀, Edge E2E를 통과했다. 실제 Codex에서 사용자 정의 `_meta` 전달은 미검증 상태를 유지한다.

## 12. UX09 — 고정 작업 폴더 중심의 위임과 경로 입력 개선

**상태: 2026-09-21 구현·자동 검증 완료.** 실제 클라우드 모델, UNC와 실제 다중 드라이브 환경 검증은 남아 있다. 아래 구현 전 기록은 결정 과정과 회귀 기준을 보존하기 위한 이력이다.

### 사용자 요구와 배경

- 사용자는 경로를 특정 표기로 다시 작성하거나 작업 폴더를 매번 전달하는 것이 아니라, MCPex가 고정 폴더 범위 안의 상대 경로와 절대 경로를 모두 같은 대상으로 처리하기를 원한다.
- 구현 전에도 `fixed`는 실행 기준 폴더를 설정값으로 고정했다. 상대 경로는 기준 폴더를 다시 선택하는 값이 아니라 그 안에서 작업할 파일을 선택하는 값이다.
- 구현 전 scoped 파일 도구는 절대 경로를 거부했고 내부 모델 도구 설명에는 실제 기준 폴더와 상대 경로 규칙을 넣었다. 이번 개선에서는 실제 절대 경로를 설명에 주입하지 않고 폴더 내부의 두 경로 표기를 모두 처리하도록 바꿨다.
- 과거 `list_files` 실패의 정확한 원인은 기록 부족으로 미확정이다. 실제 NVIDIA HTTP 500은 도구 호출 전에도 발생했다. 이 개선으로 공급자 오류까지 해결된다고 간주하지 않는다.

### 목표 동작과 역할

1. 사용자는 설정에서 에이전트의 작업 기준 폴더를 지정한다. 해당 폴더와 하위 전체가 접근 범위이며 허용 도구에 따라 읽기·쓰기가 결정된다.
2. 공개 MCP 설명과 내부 모델 도구 설명에는 실제 작업 폴더 문자열을 넣지 않는다. “설정된 작업 폴더와 하위 범위에서 상대 경로 또는 범위 내부 절대 경로를 사용할 수 있다”는 계약만 전달한다.
3. `fixed` 호출에는 별도 workspace 메타데이터나 상대 경로 변환을 요구하지 않는다. 모델이나 사용자가 어느 표기로 경로를 제공하든 MCPex가 서버 내부의 적용된 작업 폴더를 기준으로 정규화하고 경계를 검사한다.
4. 작업 내용에 파일 경로를 언급하는 것은 허용하되 그 내용이 설정된 기준 폴더를 바꾸지는 않는다. 작업 폴더 고정이 단일 파일 고정이나 하위 폴더 접근 금지를 뜻하지 않음을 UI와 도구 설명에 명시한다.

### 권장 구현안 — 범위 내부 경로 표기 유연화

- `fixed`에서 상대 경로는 기준 폴더에 결합하고, 절대 경로는 같은 기준 폴더 내부인지 검사한 뒤 허용한다. 두 표현은 같은 실제 파일로 정규화한다. 폴더 외부 절대 경로를 파일명만 추출하거나 루트에 강제로 붙여 다른 파일로 해석하지 않는다.
- 예: 기준 `C:\Work\ProjectA`에서 `src\main.ts`와 `C:\Work\ProjectA\src\main.ts`는 같은 대상이다. `C:\Work\ProjectB\main.ts`, `C:\Work\ProjectA-other\main.ts`, `..\ProjectB\main.ts`는 거부한다.
- 공통 경로 처리 대상에는 파일 도구의 `path`와 `run_command.cwd`를 포함한다. 허용 명령 목록·기대 해시·결과 크기 제한·OS 권한·링크 차단·큐 잠금 정책을 유지한다.
- 공통 처리 변경으로 `caller`에도 적용한다면 **해당 호출에서 선택한 실제 작업 폴더 내부**만 허용한다. 상위 `allowedRoots` 전체로 접근 범위를 넓히지 않는다. `caller`의 메타데이터 필요 조건과 `full`의 절대 경로 계약은 유지한다.
- 공개 MCP 설명과 내부 모델 도구 설명은 실제 작업 폴더 문자열을 노출하지 않는다. 적용 버전의 정책을 기준으로 “고정 범위”, “호출자 선택 범위”, “전체 접근” 계약을 구분하고 카탈로그와 실제 등록 설명을 일치시킨다. 시스템 프롬프트를 사용자가 편집해도 경계 검사는 유지되어야 한다.
- MCPex가 설정 경로를 설명이나 프롬프트에 새로 주입하지 않는다는 뜻이며, 사용자 입력이나 모델이 이미 절대 경로를 제공한 경우까지 숨기거나 다른 경로로 바꾸는 기능은 아니다. 도구 결과의 경로 표시는 가능한 한 작업 폴더 기준 상대 경로를 유지한다.
- 기존 정책을 삭제하거나 기존 에이전트를 `fixed`로 자동 변환하지 않는다. 신규 설정의 기본 정책을 바꾸는 일은 이번 범위에 포함하지 않는다. 사용자가 작업 폴더를 직접 선택하도록 한다.

### 구현 위치와 동기화 대상

- `packages/tools/src/index.ts`: `WorkspaceTools.safePath`에서 상대 경로와 범위 내부 절대 경로를 하나의 후보 경로로 정규화한다. `getWorkspaceToolDefinitions`에서는 실제 `workspaceRoot` 주입을 제거하고 두 표기 허용·범위 밖 거부 계약만 안내한다.
- `apps/server/src/index.ts`: 실행 작업 폴더 확정은 유지하고, `publishedToolDescription`, 카탈로그와 MCP 등록에는 실제 폴더 문자열 없이 적용 버전의 정책·범위만 표시한다.
- `apps/web/src/main.tsx`: 고정 폴더·하위 접근·경로 입력 설명. 기존 화면 구조 안에서 보완한다.
- 기존 `tests/io-diagnostics.test.ts`는 scoped 절대 경로를 무조건 거부하는 예제를 사용한다. 개선 후에는 **실제 범위 밖 절대 경로**를 거부 사례로 변경하고 범위 내부 절대 경로 성공을 별도로 검증한다. 보안 검증을 삭제해 통과시키지 않는다.
- 구현 후 실제 변경 범위에 맞춰 README, PRODUCT_SPEC, API_SPEC, IMPLEMENTATION_STATUS, TEST_PLAN을 갱신한다. 현재 문서화 단계에서는 현행 계약을 구현 완료로 덮어쓰지 않는다.

### 구현 전 확정 순서

1. `safePath`의 scoped 후보 계산을 상대 입력은 `root` 결합, 절대 입력은 그대로 정규화하도록 바꾸고, 두 경우 모두 동일한 `relative(root, candidate)` 경계·링크 재검사를 거치게 한다.
2. 파일 도구 `path`와 `run_command.cwd`가 공통 `safePath`를 계속 사용하도록 유지하고 별도 경로 해석기를 추가하지 않는다.
3. 실제 root를 설명에 넣는 `getWorkspaceToolDefinitions(..., workspaceRoot)` 전달을 제거하고 공개·내부 설명을 비노출 계약으로 맞춘다.
4. `tests/io-diagnostics.test.ts`와 `tests/p4.test.ts`에 동일 파일 상대/절대 성공, 범위 밖·유사 접두사·부모 이동·junction·caller 선택 범위·full 회귀를 추가한다.
5. UI 문구와 관련 명세를 실제 구현 결과에 맞춰 갱신한 뒤 build/typecheck/lint, 단위·통합, Edge E2E를 순서대로 수행한다.

### 구현 전 기준선 확인

- 현재 `WorkspaceTools.safePath`는 scoped root가 있으면 절대 경로를 `PATH_FORBIDDEN`으로 거부하고, 상대 경로만 root에 결합한다. 모든 파일 도구와 `run_command.cwd`가 이 함수를 공유하므로 공통 지점 한 곳을 수정하면 된다.
- 현재 서버는 실행 시 `getWorkspaceToolDefinitions(fullAccess, commands, workspace)`로 실제 workspace를 내부 모델 설명에 넣는다. UX09에서는 세 번째 인자를 제거하고 일반 경계 계약만 전달한다. 공개 MCP 설명은 현재도 실제 root를 포함하지 않으므로 새 경로 노출을 추가하지 않는다.
- 구현 전 기준선으로 `tests/p4.test.ts`와 `tests/io-diagnostics.test.ts` 16개가 통과했다. 후자는 범위 내부 절대 경로 거부를 현재 정상 동작으로 확인하므로 구현 후 성공 사례로 전환한다.

### 인수 기준

- 고정 폴더 에이전트를 MCP에서 workspace 메타데이터 없이 호출해 모의 공급자와 실제 파일 도구로 생성·읽기·수정한다. 메인 에이전트용 입력 스키마에 새 필수 작업 폴더 필드를 추가하지 않는다.
- 동일 파일의 상대/절대 경로 읽기 결과와 해시가 같고, 두 표현으로 쓰기·수정해도 같은 파일에 반영된다. 기준 폴더 자체를 가리키는 `.` 및 절대 경로의 목록 조회도 성공한다.
- 범위 밖 절대 경로, 부모 이동, 비슷한 접두사의 형제 폴더, 다른 드라이브 및 junction/심볼릭 링크 우회는 거부한다. Windows 대소문자·구분자·공백 경로를 검증하고 UNC·다중 드라이브를 시험하지 못하면 미검증으로 남긴다.
- `run_command.cwd`도 같은 경계를 지키며 미등록 명령을 실행할 수 없다. `caller` 선택 폴더 밖이지만 상위 허용 루트 안인 경로도 거부한다. `none`·`full`과 기존 잠금 동작의 회귀를 확인한다.
- 공개 MCP 설명, 내부 모델 도구 설명과 연결 정보 응답에 설정된 실제 작업 폴더 문자열이 포함되지 않는다. 설명은 상대 경로와 범위 내부 절대 경로를 모두 허용하고 범위 밖은 거부한다는 계약만 표시한다.
- 초안의 폴더 변경은 적용 전 실제 실행 범위를 바꾸지 않는다. 적용 후에만 새 범위가 실행에 사용되는지 확인하며, 경로 문자열을 공개 설명에 넣어 변경 여부를 판별하지 않는다.
- 자동 테스트 통과와 실제 클라우드 모델 입출력 성공을 따로 기록한다. NVIDIA 500이 지속되면 로컬 검증 완료·실모델 검증 실패로 남긴다.

### 구현 및 검증 결과

- 파일 도구의 `path`와 `run_command.cwd`는 scoped 범위에서 상대 경로와 범위 내부 절대 경로를 공통 `safePath`로 정규화한다. 범위 밖 절대 경로, 부모 이동, 비슷한 접두사의 형제 폴더와 링크 우회는 계속 거부한다.
- 공개 MCP 설명과 내부 모델 도구 설명에서 실제 작업 폴더 문자열을 제거하고 일반 경로 계약만 전달한다. 파일 도구 결과의 경로도 가능한 경우 작업 폴더 기준 상대 경로로 반환한다.
- `fixed`는 workspace 메타데이터 없이 적용된 고정 폴더를 사용하고, `caller`는 호출에서 선택한 폴더 안으로 제한되며, `full`은 기존처럼 절대 경로를 요구한다. 저장된 사용자 설정과 기본 정책은 변경하지 않았다.
- Windows 대소문자·혼합 구분자·공백 경로, 동일 파일의 상대/절대 읽기·쓰기·치환, `run_command.cwd`, 공개·내부 설명의 root 비노출을 회귀 검사했다.
- build, typecheck, lint, Vitest 22개 파일·69개 테스트와 Edge E2E 1개가 통과했다. E2E는 약 11.3초 후 수동 개입 없이 종료됐다.
- 실제 NVIDIA 공급자 HTTP 500은 이 경로 개선과 별개이며 해결된 것으로 기록하지 않는다. UNC·실제 다중 드라이브와 실제 클라우드 모델 호출도 미검증이다.

## 13. UX10 — 모델 선택에 프로바이더명 표시

**상태: 구현·자동 검증 완료.** 모델 표시는 프로바이더 이름을 포함하며 선택 값은 기존 model.id를 유지한다. 이름 누락 시 `프로바이더 확인 필요`, 동명 프로바이더는 비밀이 아닌 provider ID로 구분한다. 실제 사용자 데이터의 모델 식별성은 미검증이다.

- 수정 전 ModelOptions는 `label (modelId)`를 표시하고 모델 등록은 label을 modelId와 같게 저장했다. 따라서 사용자가 보고한 `모델명(모델명)`이 발생했다.
- 기본 표시는 **모델 표시명 (프로바이더명)**으로 통일한다. 사용자 지정 label이 없으면 modelId를 모델명으로 사용한다. 실제 API modelId는 상세 화면에서 별도 표시하고 표시명과 같으면 중복하지 않는다.
- 에이전트 생성/편집 등 ModelOptions 사용 지점과 모델 목록·삭제 확인에서 같은 식별 규칙을 사용한다. 선택 value와 저장 참조는 기존 model.id를 유지한다. providerId로 프로바이더명을 조회하며 ID나 API 키를 이름 대신 표시하지 않는다.
- 프로바이더명을 찾지 못하면 `프로바이더 확인 필요`로 명확히 표시한다. 동일 프로바이더명까지 중복이면 보조 식별자를 보여주되 인증값 포함 URL을 표시하지 않는다.
- 인수 기준: 같은 modelId를 서로 다른 프로바이더에 등록해 이름으로 구분 가능, 사용자 지정 label 유지, 프로바이더 이름 변경 반영, 기존 모델 선택/저장 참조 유지, 연결 데이터 누락 시 화면 오류 없음.

## 14. UX11 — Windows 보조 콘솔 창 노출 제거

**상태: 유력한 소스 누락 수정·코드 검증 완료, 실제 데스크톱 시각 검증 미완료.** DPAPI PowerShell `spawnSync`에 `windowsHide: true`를 추가했다. 비밀값 stdin 전달·CurrentUser 보호·오류 전파는 유지한다. 실제 깜빡임의 PID·부모 PID를 확인하지 않아 이 변경만으로 사용자 현상이 해결됐다고 단정하지 않는다.

- 사용자는 계속 CMD처럼 보이는 창이 떴다가 사라진다고 보고했다. 창 모양만으로 cmd.exe라고 확정하지 않는다.
- 유력 지점은 `packages/storage/src/index.ts`의 DpapiSecretStore.transform이었다. 비밀값 set/get 시 PowerShell을 spawnSync로 실행하면서 windowsHide가 빠져 있었다. 다른 주요 spawn 경로와 VBS 진입점에는 이미 숨김 설정이 있어 런처 전체를 교체하지 않았다.
- 해결안: 이 호출을 포함해 제품 내부 보조 프로세스는 windowsHide를 명시하고, PowerShell/셸의 자식 실행에도 숨김이 유지되는지 점검한다. 비밀값 stdin 전달, DPAPI CurrentUser 보호, 종료 코드 검사는 그대로 유지한다. 창 숨김을 이유로 오류를 삼키지 말고 UI 또는 비밀값 없는 진단 로그로 전달한다.
- 프로세스 이름/PID/부모 PID와 발생 시각만으로 설정 열기·인증정보 읽기/저장·모델 요청·폴링 중 어떤 동작과 연관되는지 확인한다. 프로세스 명령줄에 비밀이 있을 수 있으므로 원문을 공개 로그로 수집하지 않는다.
- 인수 기준: VBS 설정 열기, 서비스 자동 시작/재연결, 키 저장/읽기, 모델 호출 반복과 유휴 상태에서 제품이 생성하는 보조 콘솔이 보이지 않는다. 실제 Windows 데스크톱에서 확인한다. 숨김 옵션 단위 검사만으로 시각적 완료를 선언하지 않는다. 의도적으로 사용자가 연 터미널이나 등록된 대화형 외부 프로그램을 강제로 닫지는 않는다.
- 실제 원인이 외부 MCP 클라이언트의 실행 방식이면 제품 소스의 누락과 구분하여 해당 실행 설정 해결 방안을 기록한다. 현 시점에 외부 원인으로 단정하지 않는다.

## 15. UX12 — 파일 경로 기준·모호한 입력·오류 복구 명확화

**상태: 기본 템플릿·경로 모호성 검사·오류 복구 구현 및 자동 검증 완료.** 실제 클라우드 모델과 UNC·다중 드라이브 수동 시험은 미검증이다. 유연함은 같은 파일을 가리키는 표기 수용과 복구 가능한 안내를 뜻하며, 실패 시 다른 파일을 추측해 쓰는 동작을 뜻하지 않는다.

### 현재 확인과 권장 계약

- 범위 내부 절대 경로와 상대 경로는 이미 지원한다. fixed 기준 폴더와 caller가 선택한 폴더는 기존처럼 실행 전에 확정한다. UI의 허용 범위, 실제 실행 기준, input.workspace 문맥 값을 구분한다.
- 예: fixed가 `C:\Work`이고 입력 문맥이 `C:\Work\ProjectA`여도 `src/main.ts`는 현재 `C:\Work\src\main.ts`다. 원하는 파일은 `ProjectA/src/main.ts` 또는 범위 내부 절대 경로로 지정해야 한다. 모호한 문맥 값을 보고 기준 폴더를 몰래 바꾸지 않는다.
- 기본 코드 템플릿의 workspace 입력을 선택값으로 바꾸고 `작업 대상 위치(문맥 정보, 실행 기준 변경 아님)`로 설명했다. scope 누락을 수정하고 모의 공급자 요청에 scope와 실행 기준 안내가 전달되는지 확인했다. 기존 사용자 스키마·프롬프트는 자동 교체하지 않는다.
- 실제 루트 문자열을 공개 MCP 설명이나 내부 모델 설명에 자동 주입하지 않는 UX09 계약을 유지한다. scoped 모델은 `.` 목록 조회와 반환된 상대 경로를 사용할 수 있어야 한다. 로컬 설정 UI에는 실제 적용 기준 폴더와 예시를 표시한다. 사용자가 입력·파일 본문에 직접 넣은 경로까지 비공개를 보장한다는 뜻은 아니다.

| 범위 밖, 링크, OS 접근 거부                      | 원인별 코드와 안전한 설명 제공. 다른 루트 fallback이나 권한 상승 금지                                                                                                                 |
| 기대 해시 누락/충돌                              | 같은 대상 재읽기 후 변경 내용을 다시 검토하도록 안내. 현재 보호 기능을 유지하고 자동 강제 덮어쓰기 금지                                                                               |

파일 `path`와 명령 `cwd`는 공통 계약을 유지한다. UNC/드라이브/특수 경로를 새롭게 지원한다고 선언하기 전에 허용 여부와 실제 Windows 시험 결과를 남긴다.

구현은 모호한 Windows 경로를 `AMBIGUOUS_PATH`, 자동 확장하지 않는 표기를 `PATH_FORMAT_UNSUPPORTED`로 구분한다. OS의 파일 없음 오류는 기존 `ENOENT` 코드를 유지하되 실제 루트가 담긴 예외 메시지를 안전한 재탐색 안내로 바꾼다. B01 보완으로 목록 도구가 허용된 scoped는 `.` 탐색, full은 사용자가 제공한 경로의 존재하는 상위 폴더를 절대 경로로 탐색하도록 안내한다. 목록 도구가 없으면 경로 재확인만 안내한다. 해시 충돌은 같은 대상 재읽기를 안내한다. 로컬 설정 화면에 실제 초안 기준 폴더와 ProjectA 상대 경로 예시를 표시하며 MCP 공개 설명에는 폴더 값을 추가하지 않는다.

### 범위 확장이 필요한 경우

넓은 허용 루트를 유지하면서 프로젝트마다 상대 기준을 바꾸는 기능은 별도 제안이다. 필요하면 구조화된 호출 필드로 작업 하위 폴더를 선택하고 범위 검증 후 실행 스냅샷에 고정하도록 설계한다. 프롬프트의 input.workspace를 암묵적으로 권한/기준 변경에 사용하지 않는다. 새 필드 이름·caller 메타데이터와의 우선순위·잠금 범위는 **미결정**이며 이번 필수 수정 범위에 포함하지 않는다.

### 인수 기준과 인계

- 동일 파일의 상대/절대 표기로 생성·읽기·해시 기반 수정 성공, scope 실제 전달, 혼합 구분자·공백·한글·대소문자 정상 처리.
- 넓은 fixed 루트와 다른 input.workspace 조합에서 기준이 바뀌지 않으며, 같은 이름의 파일 두 개를 두고 엉뚱한 파일에 쓰지 않는지 검증.
- 범위 밖·형제 접두사·부모 이동·링크·모호한 드라이브 경로를 거부하고 모델이 실제 루트 노출 없이 오류를 구분할 수 있음.
- caller 실제 선택 폴더 밖 접근 차단, full 기존 절대 경로 계약, command allowlist·해시·잠금 회귀 유지.
- 공개 설명/자동 모델 안내/기본 진단에 실제 루트를 새로 노출하지 않음. 실제 클라우드 I/O와 로컬 모의 검증은 따로 기록.

> 후속 수동 확인: UX11의 실제 창/PID·부모 PID와 발생 동작을 대조하고, UX12는 외부 클라우드 모델·UNC·다중 드라이브 환경에서 별도 확인하세요. 선택 작업 하위 폴더 기능은 여전히 미결정이며 input.workspace로 암묵 변경하지 않습니다.
