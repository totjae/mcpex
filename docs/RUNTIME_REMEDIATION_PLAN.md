# 런타임 안정성 개선 작업 인계

## 1. 목적과 상태

2026-09-25 작성. [RUNTIME_AUDIT.md](RUNTIME_AUDIT.md)의 RTA-01–09를 구현 가능한 작업과 인수 기준으로 전환한다. 이 문서 작성 시점에는 제품 코드 수정·시험이 없었다. 이후 9개 항목을 순서대로 구현했으며 항목별 검증·잔여 조건은 [구현 상태](../IMPLEMENTATION_STATUS.md)와 [테스트 계획](../TEST_PLAN.md)에 기록한다. RTA-04의 실패 후 작업 폴더 차단·재시작 보존·명시적 확인 해제도 후속 구현했다. 원문은 정적 분석 보고서다. 장애 빈도·메모리 감소·위험 점수는 측정값이 아니며 코드 근거와 실험 결과를 구분한다.

하위 에이전트는 관련 코드와 호출부를 다시 확인한 뒤 가능한 최소 변경으로 수정한다. 감사 문서의 패치는 핵심 예시이므로 그대로 붙여 넣지 않는다. 실제 예외 변환·타입·수명주기·호환성까지 연결해야 완료다.

- fixed/caller/full, targets와 기존 경로 도구, 명령 allowlist, 해시 보호, 모델 티어, 인증·데이터 보존 계약을 유지한다. 파일/명령 작업이 살아 있는데 Promise.race로 결과만 종료하고 잠금을 풀지 않는다.
- 취소는 새 작업을 막는 협력적 중단이다. 이미 완료된 쓰기를 자동 롤백하거나 모든 OS I/O를 즉시 멈출 수 있다고 설명하지 않는다. 부분 변경 기록은 유지한다.
- 실제 사용자 DB·비밀값·실행 중 서비스는 테스트에 사용하지 않는다. 임시 데이터·합성 파일·모의 공급자를 우선 사용하고 시험 자식/타이머/핸들을 정리한다. 유료 모델 호출·사용자 서비스 재시작은 이번 인계의 기본 검증에 포함하지 않는다.
- 새로운 의존성, 범용 작업 엔진, DB worker 전면 전환을 선제 도입하지 않는다. 공통 실행 경계와 기존 도구를 활용한다.

## 3. 단계별 작업과 인수 기준

### RTA-03 — 취소와 시간 초과 후 후속 작업 차단

**위치:** packages/runtime/src/index.ts의 runToolLoop/RunQueue, packages/tools/src/index.ts의 파일·대상 도구/검색/명령, apps/server/src/index.ts의 접수·bindTargets·실행 dispatch.

- 모델 응답 직후, 각 도구 호출 직전, 도구 오류 처리에서 abort를 검사한다. 취소 예외를 일반 도구 실패 JSON으로 삼켜 다음 호출을 실행하지 않는다.
- 호출자 signal을 연결할 때 이미 aborted인 상태도 전달한다. bindTargets 같은 await 전후와 큐 제출 경계를 확인한다. 실패 시 이벤트·실행 상태가 미완료로 남지 않게 한다.
- 파일·대상 도구에 signal을 일관되게 전달한다. 긴 읽기/검색/열거와 변경을 시작하기 직전, 임시 파일을 실제 대상에 반영하기 직전 등 적절한 지점에서 검사한다. 이미 변경이 반영된 뒤 단순 취소 검사 때문에 성공 변경 기록을 잃지 않도록 실제 반영과 기록 순서를 설계한다.
- CANCELLED와 DEADLINE/QUEUE_TIMEOUT/EXECUTION_TIMEOUT 등 기존 종료 원인·부분 변경/과제 미검증을 유지한다. 파일 작업 종료 전 잠금을 해제하지 않는다.

**검증:** 한 모델 응답의 첫 도구를 제어 가능한 Promise로 대기시키고 취소한 뒤 두 번째 쓰기/명령 시작이 0회인지 확인한다. 모델이 취소를 무시하고 늦게 응답하는 경우, 접수 전 취소, bindTargets 중 취소, 쓰기 반영 전/후 취소, 시간 초과를 구분한다. 타이머의 짧은 sleep에만 의존하지 않는다.

### RTA-04 — 명령과 종료 보조 프로세스의 수명 정리

**R14 수정 반영(2026-09-25):** 모든 기록된 조상 기준 후손 탐색과 새 식별자의 영속 보존을 구현했다. verify는 빈 목록도 추적 공백으로 간주해 409로 차단을 유지하고, 독립 OS 확인 후 수동 해제만 허용한다. 정상 taskkill 성공·정상 종료의 자원 해제는 유지한다. 임시 Windows 3세대 생존 손자 탐지와 임시 DB/API의 반복 발견·재시작·명시적 해제 회귀를 수행했다. 실제 사용자 서비스·DB 및 원자적 PID 종료 경합은 미검증이다. 아래 후속 검토는 수정 전 발견 이력이며 최신 시험 결과는 TEST_PLAN.md를 따른다.

**2026-09-25 후속 검토:** [전체 구현 검토 R14](IMPLEMENTATION_REVIEW.md)에서 종료된 자식 아래의 새 손자가 잔존해도 `survivingTree`가 빈 목록을 반환하는 입력을 재현했다. 기록된 모든 식별자 기준 후손 추적, 재확인 시 발견한 후손 보존 및 불완전 조회의 해제 정책을 보완하고 API·재시작 회귀를 추가해야 한다. 기존 차단 구현과 시험 통과만으로 본 항목의 인수 완료를 선언하지 않는다.

**위치:** WorkspaceTools.runCommand 및 관련 명령 회귀.

- 단일 종료/정리 경로를 두고 child close/error에서 timeout과 abort listener를 제거한다. 이미 취소된 signal 및 safePath 완료 후 취소를 spawn 전에 검사한다.
- terminate는 여러 번 호출돼도 중복 taskkill을 생성하지 않고 완료한 child에는 동작하지 않는다.
- taskkill의 error/exit/timeout을 처리하고 서비스가 미처리 error로 종료되지 않게 한다. 실패를 숨기지 않되 자식/하위 프로세스 종료가 확인되기 전에 단순 완료 처리하거나 잠금을 풀지 않는다. 제한된 fallback과 종료 실패 상태를 정하고 테스트한다.
- Windows 숨김 실행·shell false·최소 환경변수·출력 상한·명령 allowlist를 유지한다. 새 관리자가 필요하거나 무관한 프로세스를 종료하는 방식으로 바꾸지 않는다.

**검증:** 정상 완료 후 abort 시 종료 호출 0회, 이미 취소된 요청의 spawn 0회, taskkill 시작 실패/실패 exit/무응답, 원 명령 시작 실패, 반복 취소, 출력 상한을 시험한다. 실제 시험 프로세스 트리의 종료·listener/타이머/잠금 정리도 확인한다. mock만으로 Windows 하위 프로세스 종료 완료를 선언하지 않는다.

**후속 구현 및 운영:** Windows에서는 `Win32_Process`의 PID·부모 PID·생성 시각을 수집하고, 종료 직전 부모 PID의 생성 시각을 재확인한다. 일치하지 않거나 조회할 수 없으면 PID만으로 `taskkill`하지 않는다. `taskkill` 성공 후에는 모든 기록된 조상 아래 새로 관측되는 후손의 잔존 여부를 확인한다. 실패·조회 불가 시 부모 직접 종료만으로 트리 종료를 추정하지 않고 `COMMAND_TERMINATION_FAILED`로 마감한다. 해당 작업 폴더와 겹치는 작업 및 전체 접근 작업은 `WORKSPACE_BLOCKED`로 거절한다. 차단 기록은 로컬 DB 설정에 보존해 서비스 재시작 후 다시 적용한다. 관리 화면의 **설정 및 데이터 관리 → 프로세스 상태 재확인 (차단 유지)**는 새 후손을 저장하고, 빈 목록도 추적 공백 때문에 차단을 유지한다. OS 도구에서 전체 트리를 독립 확인한 운영자만 경로 재입력·확인 문구로 수동 해제한다. 식별 기록이 있는 경우 현재 OS 조회·저장 실패에도 해제하지 않는다. 시간 경과만으로 해제하지 않는다. 생성 시각 재검사와 확인은 PID 재사용 위험을 줄이지만, 검사와 `taskkill` 사이의 OS 수준 원자성까지 보장하지는 않는다. DB 기록 실패, 극단적 프로세스 생성 경합은 별도 운영 검증이 남는다.

### RTA-07 — SSE 오류 격리와 느린 연결 처리

**위치:** apps/server/src/index.ts의 실행 이벤트 SSE, storage.listRunEvents 관련 호출.

- timer가 호출하는 pump에도 예외 경계를 적용해 해당 연결만 종료한다. 로그에는 원시 payload·인증값을 넣지 않는다.
- 응답 close/error, 정상 종료, 예외 모두에서 timer와 drain listener를 정리한다. 요청/응답 객체의 close 의미를 실제 사용하는 Node/Fastify 버전에서 확인한다.
- write(false)이면 다음 쓰기와 조회를 멈추고 drain 후 재개한다. 현재 write로 이미 수락된 이벤트를 중복 전송하지 않도록 cursor를 관리한다.
- SSE 전용 이벤트 조회에 배치 상한을 적용한다. 같은 조회 함수를 쓰는 targetChanges/티어 집계가 첫 배치만 읽어 기록을 누락하지 않도록 한다. terminal 실행도 남은 이벤트를 모두 보낸 뒤 닫는다.

**검증:** 첫 호출과 후속 timer의 DB 오류/잘못된 JSON, 느린 reader, 중간 연결 종료, 여러 배치, terminal 도달, Last-Event-ID 재연결에서 서버 생존·순서·중복/누락 없음과 정리를 확인한다. 이벤트 수가 배치보다 많은 실행의 관리 화면 집계도 검증한다.

### RTA-02 — DPAPI 비동기 처리와 비밀 저장 경합 보호

**R15 수정 반영(2026-09-25):** 소유자를 증명할 수 없는 잠금과 종료된 소유자의 잠금을 실행 중 자동 삭제하지 않는다. 빈/부분 잠금 생성 중 경합에서 기존 파일을 덮어쓰지 않으며, 최대 10초 후 `SECRET_STORE_LOCKED`로 실패한다. 별도 프로세스 set/set·set/delete, 작성자 중단 후 명시적 복구를 임시 데이터로 검증했다. 운영 복구는 서비스를 완전히 중지하고 같은 데이터 폴더의 모든 작성자가 종료됐는지 확인한 뒤 `secrets.lock`을 보관 위치로 옮기고 다시 시작한다. 잠금 파일만 제거하며 `secrets.json`은 보존한다. 자동 회수의 OS 수준 원자성이 없어 이를 안전한 정책으로 선택했다. 아래 독립 검토는 수정 전 이력이다.

**2026-09-25 독립 검토 R15:** 잠금 생성 직후 빈 내용을 파싱 실패→stale로 처리해 살아 있는 작성자의 잠금을 삭제하는 경합을 재현했다. 두 저장 성공에도 한 키가 유실된다. [전체 구현 검토 R15](IMPLEMENTATION_REVIEW.md)의 수정 기준·빈/부분 잠금 및 동시 저장 회귀를 먼저 수행한다. 기존 동시 저장 시험 통과는 이 생성 경계를 검증하지 못했다.

**위치:** packages/storage/src/index.ts의 SecretStore/DpapiSecretStore 및 서버·CLI·시험의 모든 get/set/delete 호출부.

- 동기 PowerShell 대기를 비동기 spawn/execFile로 바꾸고 timeout·stdout/stderr 상한·stdin 오류 처리를 연결한다. 숨김 실행·CurrentUser DPAPI·stdin 비밀 전달을 유지한다.
- 모든 호출부를 await 기반으로 전환한다. 초기 인증, bootstrap/CLI open/mcp, credential 조회·교체·삭제, 실행 접수, 가져오기 등 호출 흐름 전체를 조사한다.
- 비동기화로 생기는 secrets.json 읽기-수정-쓰기 경합을 보호한다. set/set, set/delete, 읽기 중 교체와 실패 시 기존 파일 보존을 검증한다. 같은 dataDir을 CLI와 서버가 함께 사용할 수 있으므로 프로세스 내부 mutex만으로 충분하다고 가정하지 않는다. 기존 단일 작성자 구조 또는 프로세스 간 쓰기 조정 중 실제 호출 구조에 맞는 방법을 선택한다.
- 오류 응답에 프로세스 입력/출력·명령줄·인증값을 포함하지 않는다. 평문 fallback은 추가하지 않는다. 시간 초과 후 자식 정리를 보장한다.

**검증:** 지연/무응답/실패/과대 출력/stderr/깨진 stdin을 모의하고 다른 health·취소 timer가 진행하는지 확인한다. 합성 비밀값 동시 저장·삭제·읽기와 초기 로컬 토큰 생성 경쟁을 시험한다. 실제 Windows DPAPI 합성 값 round-trip도 확인한다.

### RTA-01 — 스키마 검증기 보관량 제한

**위치:** apps/server/src/schema.ts의 전역 Ajv 및 compile 진입점.

- 설치된 Ajv의 실제 캐시 보유 동작을 먼저 확인한다. validateUserSchema/입출력 검증의 컴파일을 공통화하고 내용 기반 재사용과 항목 수·키/스키마 바이트 예산을 둔다.
- 외부 Map만 제한하고 Ajv 내부 객체 캐시를 남겨두지 않는다. 제거 API가 메타스키마·참조·실패 컴파일에 미치는 영향을 확인한다. 기존 입력 크기·깊이·허용 키워드·오류 변환은 유지한다.
- 직렬화 키의 순서 차이가 중복을 만들 수 있으나 완전한 JSON canonicalization 라이브러리부터 도입하지 않는다. 최대 보관량을 먼저 보장하고 키 정책을 명시한다.

**검증:** 같은 내용의 새 객체 반복은 컴파일 재사용, 예산을 넘는 서로 다른 스키마는 제한된 보관량, 실패 스키마 반복도 누적 없음, 퇴출 후 재컴파일·기존 입력/출력 오류 계약 유지. 컴파일 횟수와 보관 개수를 결정적으로 검증하고 힙 추세는 별도 보조 측정으로 남긴다.

### RTA-05 — 공급자 실제 수신량과 누적 대화 제한

**위치:** packages/providers/src/index.ts의 모든 어댑터 generate/listModels 및 runtime 도구 루프.

- 성공·오류 응답 모두 공통 제한 읽기를 사용한다. Content-Length가 없거나 거짓이어도 실제 디코딩된 수신 바이트를 세고 한도를 넘으면 읽기를 취소·해제한다. timeout/사용자 취소와 크기 초과 오류를 구분한다.
- 텍스트 수신·JSON 파싱·도구 인자 처리의 기존 오류 계약을 유지한다. reader 정리 중 오류가 최초 제한 초과 원인을 덮어쓰지 않도록 한다.
- 단일 응답 상한과 별개로 모델 중간 메시지·도구 인자·도구 결과를 포함한 누적 대화 예산을 검사한다. 예산 초과 시 명시적으로 종료하며 사용자 지시나 도구 메시지 쌍을 임의 삭제하지 않는다. 기존 최종 출력 제한은 유지한다.

**검증:** 경계 바로 아래/같음/초과, Content-Length 없음/거짓, 큰 오류 body, 압축 응답, 멀티바이트 문자 경계, 중도 취소, 모델 목록 및 각 어댑터 경로를 확인한다. 작은 응답 여러 번으로 누적 예산에 도달하는 루프도 검증한다. 실제 OOM을 발생시키는 시험은 필요하지 않다.

### RTA-06 — 디렉터리 열거를 제한 내에서 수행

**위치:** WorkspaceTools.listFiles/searchText의 walk.

- readdir 전체 배열 대신 opendir iterator 등으로 필요한 만큼 읽고 조기에 중단한다. 기존 제외 폴더·경로/링크 경계·출력 형식을 보존한다.
- 취소, 결과 수·바이트·깊이 및 실제 탐색 항목 수 제한을 공통 전달한다. 결과에 포함하지 않은 항목을 무한히 훑지 않도록 탐색 예산을 구분한다.
- break·예외·취소·재귀 반환에서 디렉터리 핸들을 닫는다. iterator 자동 정리와 명시적 close가 충돌하지 않도록 한다.

**검증:** 결과 상한보다 큰 합성 폴더, 제외 항목이 많은 폴더, 깊은 폴더, 탐색 도중 취소/권한 오류에서 조기 종료·truncated 표시·핸들 정리를 확인한다. 정확한 파일시스템 열거 순서를 새 계약으로 추가하지 않는다.

### RTA-08 — 만료 데이터 정리 배치와 실행 수명

**위치:** storage.purgeExpiredRunContent 및 서버 시작/설정 저장/종료.

- LIMIT 기반 배치 트랜잭션으로 ID 적재량을 제한하고 배치 사이 setImmediate 등으로 I/O에 양보한다. queueMicrotask 반복은 대안이 아니다.
- 보존 cutoff를 한 정리 실행에서 고정하고 진행 중 실행을 삭제하지 않는다. 이벤트·본문·만료 표식의 일관성과 SSE 410/변경 기록 확인 불가 계약을 유지한다.
- 주기적 정리를 추가할 경우 중복 실행 방지와 서비스 종료 시 timer/진행 작업 정리를 함께 구현한다. 단일 실행의 매우 많은 이벤트 삭제 비용도 측정하고 무조건 배치 100건이면 충분하다고 가정하지 않는다.

**검증:** 여러 배치의 만료/미만료·진행 중 기록, 설정 변경과 정리 요청 중첩, 정리 도중 오류/서비스 종료, API 응답 기회와 삭제 결과 일관성을 확인한다. 기록 메타데이터를 임의로 삭제하지 않는다.

### RTA-09 — 만료·대체 세션 정리

**위치:** 서버 sessions Map과 bootstrap 교환/세션 인증.

- 새 세션 생성 시 만료 항목을 제거하고 같은 브라우저의 이전 쿠키 세션을 대체한다. 유효한 다른 브라우저 세션을 일괄 제거하지 않는다.
- 기존 TTL·HttpOnly/SameSite·CSRF·일회용 bootstrap·인증 오류를 유지한다. 활성 세션 수 제한이나 별도 타이머는 측정/제품 요구가 있을 때만 추가한다.

**검증:** 가상 시각으로 반복 생성·만료·동일 쿠키 교체·다른 브라우저 유효 세션을 확인한다. 마지막 접속 후 즉각 Map 청소까지 구현하지 않았다면 그 한계를 명시한다.

## 4. 수치와 오류 계약의 결정

감사 예시의 캐시 128개, PowerShell 10초/1 MiB, 응답 2 MiB, 정리 100건은 **확정 요구값이 아니다**. 구현자는 기존 payload/스키마 제한과 정상 시험을 근거로 초기값을 정하고 API_SPEC/ARCHITECTURE 등 관련 문서에 기록한다. 누적 대화 예산·주기적 정리 간격도 같은 방식으로 결정한다. 사용자 선택이 꼭 필요한 제품 변경이 아니면 사소한 수치마다 작업을 멈추지 않는다.

새 오류 코드가 필요하면 취소·시간 초과·크기 초과·프로세스 종료 실패를 구분하고 MCP 결과/UI에 연결한다. 예상하지 못한 오류를 전부 성공/취소로 바꾸거나 반복 모델 요청으로 숨기지 않는다.

## 5. 검증 운영과 완료 보고

- tests가 빌드된 workspace 패키지를 참조하므로 소스 변경 후 관련 패키지 또는 전체를 빌드하고 시험한다. 기존 R13 대상 통합 시험은 기본 5초 제한으로 실패한 이력이 있다. 시나리오 분리 또는 합리적인 개별 상한으로 안정화하고 기본 전체 명령의 결과를 보고한다. 진단용 timeout 확대 통과를 기본 명령 통과로 대체하지 않는다.
- 각 단계 관련 시험 후 최종 build/typecheck/lint, 전체 Vitest, Edge E2E를 수행한다. 무관한 코드를 고쳐 검사 범위를 불필요하게 넓히지 않는다.
- 부하 시험은 합성 데이터와 통제된 크기로 수행한다. 힙·event-loop 지연·프로세스/핸들/캐시 개수의 전후 관측을 기록하되 실행 환경·반복 수·측정 방법을 함께 남긴다. 재현하지 못한 OOM/Crash 빈도나 감소율을 확정 수치로 쓰지 않는다.
- 각 RTA 항목을 계획/진행/구현 완료/검증 완료/일부 미검증으로 기록한다. 원문 감사에는 수정 전 근거를 보존하고 후속 상태를 연결한다. IMPLEMENTATION_STATUS/TEST_PLAN/필요한 API·운영 명세를 동기화한다.
- 최종 보고: 항목별 수정 요약, 수행 명령과 결과, 장애 모의·실제 Windows 시험의 구분, 남은 미검증, 기본 전체 시험 실패 여부를 제시한다. 실제 사용자 서비스 재시작이 필요한지도 별도로 알린다.
