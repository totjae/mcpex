# 구현 계획

## 1. 실행 원칙

설계 기준선 v1을 구현한다. P0~P5의 구성 요소 구현 후 전체 검토에서 확인한 연결 누락을 R01부터 순서대로 보완하고 있다. 각 단계는 작동하는 수직 흐름과 인수 조건으로 끝낸다. 단계 완료 시 IMPLEMENTATION_STATUS.md와 TEST_PLAN.md를 실제 결과로 갱신한다. 테스트가 없는 기능은 검증 완료로 표시하지 않는다.

P0→P1→P2→P3→P4→P5→P6 순서로 구현한다. P3까지를 내부 응답형 알파로 사용할 수 있으나 v1 완료는 P6 인수 후다. P4 필수 기능과 다양한 프로바이더·로컬 연결을 영구 제외한 채 전체 v1 완료라고 하지 않는다.

## 3. 첫 구현 작업의 구체 범위

1. 루트 package.json과 workspace 설정, .gitignore, tsconfig, lint/format 설정을 만든다.
2. contracts에서 오류·ID·상태 DTO를 정의한다.
3. storage에 version 1 migration, 데이터 디렉터리 잠금, SecretStore를 구현한다.
4. server의 /health, 인증 bootstrap·교환, 기본 오류 응답과 종료 처리를 만든다.
5. web의 메뉴와 빈 상태, 인증 접속을 연결한다.
6. cli의 serve/open을 연결하고 개발·빌드·정적 검사 명령을 제공한다.
7. P0 검증 결과 및 설치된 정확 버전을 기록한다. 아직 모델/MCP를 호출하지 않아도 된다.

P0 의존성 설치 실패 시 원인을 기록하고 같은 기술의 지원 버전부터 확인한다. 주요 기술 교체가 필요하면 ARCHITECTURE.md를 실제 결정에 맞게 갱신한다. 임의로 구형 프로토타입을 통째로 복사하지 않는다.

## 4. 릴리스 인수

사용자가 프로바이더와 모델을 등록하고, 같은 모델로 서로 다른 템플릿의 에이전트를 두 개 생성하고, 수정·시험·활성화하여 MCP에서 각각 호출할 수 있어야 한다. 실행 중 프롬프트 변경은 현재 작업에 영향을 주지 않아야 한다. 서비스 재시작 후 설정·기록이 유지되고 실행 중이던 작업은 interrupted로 표시되어야 한다.

클라우드 실제 인증이 없으면 모의 테스트는 완료할 수 있으나 해당 실연동은 미검증으로 남긴다. 비용이 발생하는 실연동 시험은 사용자가 선택·제공한 연결에 한해서 수행한다. 기존 gemma-agent의 테스트는 MCPex 인수 결과가 아니다.

## 5. 후속·보류

후속 검증 모델의 판정 스키마, 자동 재작업 정책, OS sandbox 방식, 외부 실행기 지원표, 원격 배포 인증, 설치 프로그램 배포 방식은 아직 확정하지 않는다. v1 구현을 막는 항목은 아니다. 사용자별 API 키·실제 모델 ID·작업 폴더는 제품 설정 입력이며 설계 미결정으로 취급하지 않는다.
